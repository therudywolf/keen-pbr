# Forest-PBR Stabilization & Cleanup Plan — 2026-05-28

> Source: user request after a destabilization episode where over-aggressive
> list audit + helper-script accretion broke YouTube on phones. Lists restored
> from pre-audit snapshot; YouTube works again. This plan tracks what's left
> to do, with strict guardrails to avoid a repeat.

## Cardinal rules (mandatory)
1. **One atomic change per step.** No "while I'm here" additions.
2. **Snapshot before every change** (config.json, iptables save, ipset list).
3. **User OK between stages** — no auto-progression to next stage.
4. **Rollback if acceptance fails** — don't try to patch on top, restore the snapshot.
5. **Every stage produces a short report** (what changed, before/after metrics, manual-test ask).

## Acceptance criteria (applied to every stage that touches the live router)
- `forest-pbr status` → `Overall: OK` (not DEGRADED).
- `sysctl net.netfilter.nf_conntrack_fastnat` → `0`.
- `/opt/usr/bin/forest-pbr-autocheck` for youtube/gemini/telegram/instagram via VPN → 2xx/3xx (no VPN_FAIL).
- Manual: user confirms YouTube/Gemini work on **PC + iPhone + Android**.
- `iptables -t mangle -L KeenPbrTable -nv | grep kpbrm_X.*br0` shows non-zero counters within 60 s of traffic.

## Red lines (do not touch unless plan explicitly says)
- Domain lists content (only Stage 8 grooms them, only with explicit per-list OK).
- Routing rules (rule 0 = rostelecom; rule 1 = forestserver_ru) — no list reshuffling.
- forest-pbr daemon C++ behaviour around firewall_runtime and PBR mark-set — optimizations only with measurable, isolatable wins.
- ListWarmer interval (default 600 s) — only tune in Stage 6 with profiling data.
- DoT-block FORWARD rule (port 853 from LAN) — stays.

## Snapshots
- `.claude/baseline-config.json` — config at start of plan.
- Per-stage: `.claude/snapshots/before-stage-N-YYYYMMDD-HHMMSS.json`.
- All gitignored; user can copy them off-router for safekeeping.

## Stage 3 — ListWarmer verify
**Goal:** Confirm the C++ ListWarmer that we shipped is actually firing every 600 s and populating ipsets. If broken, decide between fix or revert.

**Steps**

## Stage 4 — FASTNAT-conntrack flush mechanism
**Goal:** When config or ipsets change in a way that should alter routing, stale `[FASTNAT]` conntrack entries with `mark=0` keep traffic on the old path. Need a proper way to invalidate them.

**Two approaches; we'll try them in order.**

### 4a — Add `conntrack-tools` from Entware-mod-fork or build it
1. Check `opkg list | grep conntrack` (might be in a non-default repo).
2. If absent: cross-build `conntrack-tools` mipsel-3.4 .ipk from source, deploy.
3. If installed, daemon (or a small helper) calls `conntrack -D -m 0x100000ab` (the FASTNAT mark mask) on config-apply.

### 4b — If conntrack-tools not feasible, kernel netlink from daemon
1. forest-pbr daemon adds a tiny netlink-conntrack helper (`libnl-3` is already linked).
2. On config-apply, walk conntrack table; for any entry with `[FASTNAT]` flag *and* a destination IP that's in any `kpbr*d_*` ipset, delete the entry.
3. ~150 LOC C++. Re-uses existing libnl dependency.

**Steps (after picking a)/b))**
- Implement the chosen mechanism.
- Hook into daemon's "firewall reapply" path (SIGUSR1 today; should automatically include flush).
- Unit-test the flush logic with mocked netlink (4b).
- Deploy. Verify: change a list, send SIGUSR1, observe conntrack count of `[FASTNAT]` entries drops.

**Acceptance:** Pre/post test: add a domain to a list, reapply, FASTNAT count for relevant flows decreases.

**Rollback:** Remove the hook; daemon behaves as before (stale flows expire naturally over hours).

**Risk:** Medium. Conntrack manipulation can affect existing connections; need careful filtering.

**Estimated time:** 2 hours (4a if available) — 4 hours (4b).

## Stage 6 — C++ daemon optimization (detail)
**Goal:** Router "не вывозит" — reduce daemon CPU + memory + I/O footprint measurably.

### 6.1 — Profile on the live router
- `top -b -n5 -p $(pgrep forest-pbr)` — sample CPU%, RSS.
- `cat /proc/$(pgrep forest-pbr)/status` — VmRSS, VmSize, Threads, VmData.
- `cat /proc/$(pgrep forest-pbr)/smaps_rollup` (or smaps + summarize) — heap vs file maps.
- `pidstat -p $(pgrep forest-pbr) 5 6` — CPU usage over 30 s.
- `ls -la /proc/$(pgrep forest-pbr)/fd | wc -l` — FD count.
- `strace -c -p $(pgrep forest-pbr) -e trace=read,write,open,openat,stat,fork,execve` for 10 s — syscall counts.
- Capture all of above to a numbers report.

### 6.2 — Identify hotspots, in order of likely impact
- **dnsmasq.sh exec frequency**: the conf-script is invoked by dnsmasq on every config reload. If forest-pbr's `restart_dnsmasq` is being called more than needed, that's pure waste. Look at the daemon's reload triggers and de-dupe.
- **ListWarmer**: subprocess `ipset restore` per domain × ~969 domains every 10 min. Measure CPU time. If high, batch ALL families AND lists per pass into ONE `ipset restore` invocation.
- **REST API server**: the embedded HTTP server is always-on. If user doesn't hit it (he's mostly using CLI now), disable via `daemon.api.enabled = false` config flag.
- **Frontend static serving**: even when not visited, the file maps are loaded. Switch to headless package (`forest-pbr-headless` we already build) — no web UI binary.
- **Resolver health TXT poll**: every 30 s. Could go to 120 s if no observed breakage.
- **JSON config re-parse on every reapply**: cache parsed Config struct, invalidate only on file mtime change.
- **Verbose logging**: review every `log("...")` call site, downgrade DEBUG-level to trace.

### 6.3 — Apply optimizations
Targeted patches, one PR per optimization (so we can A/B which one moved the needle):
- O1: Switch user to `forest-pbr-headless` package (immediate, no code change — just deploy different .ipk). Probably the single biggest RSS reduction.
- O2: ListWarmer cross-list batch (single `ipset restore` per pass, not per domain).
- O3: Resolver health interval 30 s → 120 s (config flag, default 120).
- O4: De-duplicate dnsmasq restarts within a short window.
- O5: Cache parsed Config struct.
- O6: Compile with `-Os` instead of `-O2` (smaller binary, slightly slower per op but less I-cache pressure on MIPS).

### 6.4 — Re-profile, document gains
Before/after table.

**Acceptance:**
- Daemon RSS drops below 80 MB (currently ~98 MB).
- Load avg with daemon idle (no traffic) drops measurably (currently ~1.0).
- `forest-pbr` binary on disk smaller.

**Rollback:** Per-optimization git revert. Keep what helps.

**Risk:** Medium. Each optimization has its own risk; isolating them lets us bisect.

**Estimated time:** 3-5 hours, including profiling and per-O verification.

## Stage 7 — Router housekeeping
**Goal:** Free disk + RAM that's been accreting from operational cycles.

**Steps**
1. Remove old `/opt/etc/forest-pbr/config.json.bak-*` (keep only the most recent + the baseline taken in Stage 0).

4. Truncate `/opt/var/log/keen-pbr.log` if it still exists (we left it as archive earlier).
5. Apply Keenetic conntrack sysctl from `docs/router-tuning.md`:
   - `net.nf_conntrack_max = 65536`
   - `net.netfilter.nf_conntrack_buckets = 16384`
   - Persist via `/opt/etc/init.d/S99-localtune`.

**Acceptance:** `df -h /opt` shows freed space; `free -m` shows lower committed; conntrack table can handle 65k flows.

**Rollback:** Files are backups — no rollback needed. sysctl changes can be reverted by editing the init script.

**Risk:** Very low.

**Estimated time:** 20 minutes.
